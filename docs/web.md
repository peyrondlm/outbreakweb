# Web: pre-menu, controls, memory card and local server

Branch `outbreak` of `ps2-web-recomp/`. Files: `web/shell.html` (the game page, used by emscripten as its shell), `web/index.html` (game selector), `scripts/serve.py` and `run-local.sh`.

## Local server with both games
- `serve.py` accepts two forms:
  - `serve.py <build> <disc> [port]`: one game at `/`, as before.
  - `serve.py file1=build/web-outbreak1,games/outbreak1/disc.iso file2=build/web-outbreak2,games/outbreak2/disc.iso [port]`: each game under `/<name>/`, `/games.json` lists them (serial read from the build's `boot.txt`, `ready` if the `.wasm` and the disc exist) and `/` serves `web/index.html`. `/file1` redirects to `/file1/` so relative URLs (`disc.iso`, `ps2web.wasm`) resolve.
- All responses carry `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy: same-origin`.
- `run-local.sh` serves every built game that has a `disc.iso`.
- Both games share the origin (`localhost:8620`), so localStorage and IndexedDB are shared too. That is why the memory card is separated per game (below).

## Memory card per game
- The runtime always opens `/memcard/Mcd001.ps2` (`host/web.cpp`). IDBFS names the IndexedDB database after the mount point.
- The page reads `boot.txt` to learn the serial. File #1 (SLUS-20765) keeps mounting IDBFS at `/memcard`, so earlier saves are preserved. File #2 (SLUS-20984) mounts at `/memcard-SLUS-20984` and creates a symlink `/memcard` to that path. An unknown serial uses `/memcard`.
- In the pre-menu you can export (`outbreak-file1.ps2` / `outbreak-file2.ps2`), import (validates 8,650,752 bytes and the header "Sony PS2 Memory Card Format ") and delete (asks for confirmation; only before starting). During the game, importing reloads the page.

## Controls
- The keymap is a list of actions (PS2 pad bit or stick axis) with one key per action. Only changes from the default are stored in localStorage (`reo-keys-v1`). Reassigning a key already in use swaps the keys of the two actions. Del leaves the action without a key and Esc cancels. F1, F, Esc, F5, F11 and F12 are reserved.
- Key names use `navigator.keyboard.getLayoutMap()` when available, so AZERTY or QWERTZ show the real letter.
- Keys only reach the game once it is running, so the menu keeps Tab, Space and Enter.
- F1 or the "Controls (F1)" bar button shows or hides an overlay with the current map. Before starting, F1 jumps to the table.
- Default keyboard (changed from the previous one: arrows = d-pad, IJKL = stick, Z/X/A/S):

## Network
- The indicator shows in the pre-menu and in the bar. Before starting, it opens a short WebSocket to the gateway (`?gateway=` or `ws://<host>:8765/eth`) and closes it. During the game, it follows the runtime's `[net]` messages (`connected to`, `gateway closed`, `cannot reach`). With `?nonet` it shows "Network disabled".

- **Player name (2026-10-16):** field in the Network card, `^[A-Za-z0-9]{1,15}$` (length and characters the game accepts: see protocol.md §6.4), stored in `reo-net-name`. On first start with a name, `reo-net-token` (32 hex) is created. Pressing Start passes `--env PS2_NET_ACCOUNT=<name>` and `--env PS2_NET_PASSWORD=<hex(SHA-256("reo-web:"+name+":"+token))[0:12]>` (the web runtime accepts `--env K=V` in `host/web.cpp`; `Module.ENV` does not work because it is fixed earlier). On-screen warning: the token identifies the player in that browser and, if deleted, the name is lost. Without a name nothing is passed and the game asks for the password. With `?nonet` the field is disabled. SHA-256 in own JS (verified against `sha256sum`).

## Background tabs (2026-10-17)
- **Bug:** with the window hidden, minimized or occluded (alt-tab, another window on top: Chrome on Windows marks those windows `hidden`) the game froze, and online it froze the other client too.
- **Cause:** the main-thread render loop (`host/web.cpp`, `wait_shown` -> `ps2web_wait_shown`) waited for a `requestAnimationFrame` per present, and `gs::post_present` (`runtime/src/gs/gs.cpp`) blocks the emulation thread when more than 2 presents are unshown. With the page hidden rAF does not run (measured: 0/s), so emulation stayed blocked. There were no blur/visibility listeners pausing anything (`blur` only releases keys). Nothing else depended on main-thread timers: emulation is a pthread (worker) paced with `usleep`/audio ring, `browser_yield` uses MessageChannel and waits use `Atomics.waitAsync`.
- **Fix:** `ps2web_frame_done` does not arm the wait if `document.hidden`; `visibilitychange` to hidden releases a pending wait; a minimal Worker (blob, `setTimeout` 50 ms; worker timers are not throttled like the page's) releases a frame that rAF never showed (an occluded window that stays `visible`). `pace()`: if the AudioContext stops draining the ring (>100 ms with >80 ms queued) it switches to the clock (`g_audio.active=0`; the worklet sets it back to 1 when running) instead of freezing. On return: `audio.resume()` if suspended and an `st.throttled` notice in the bar if it emulated at <40 fps while hidden. No lag accumulates: `pace()` resets the clock if it falls >200 ms behind.
- **Evidence:** (local evidence, not published) a CDP test script: File #2 in Chrome with a really minimized window: 60.0 fps visible, 60.0/60.0 fps hidden (rAF 0/s, audio `running`), 60.0 on return. File #1 headless with another tab in front: same as the control run without hiding.

    - `online`: names and anonymous IPs that polled in the last 20 s;

    - Per-name and per-IP rate limits (429, verified).

    - Text is never HTML: the server stores it as is (JSON-escaped) and the page inserts it with `textContent` (verified: a `<b>` appears literally).
  - **Transport:** polling every 3 s (15 s with the tab hidden or no server), through `serve.py --api`. It is the simplest thing that passes through the current proxy, which does not stream: SSE or WebSocket would force changing `proxy_api`. `serve.py` did not need changes.

    - KkService already forwards the game's room chat (type `0x0F|0x0400`, protocol.md §6.8).
    - Web -> game: ChatService would have to ask KkService to inject a chat `0x0F` to the members, with the writer's name (hypothesis: the game shows only ASCII and short texts).
    - Game -> web: KkService would publish what it forwards into the `room:<id>` channel.

## Default name, expiring chat, File #2 online and full gateway (2026-10-20, outbreak `a356c02` + `46dc385`; server `cf7050c`)

## Slow disc reads: minutes-long loads and audio that never returns (2026-10-26, outbreak `fdf2bc1`) — not deployed
- Report (from a player in Europe, Chrome/Windows, File #1): gaps of 25-100 s between disc reads ("5 minutes to load") and, after a cutscene, voices and cutscene audio never come back (also with another browser and an empty card).
- **How it read (before):** `host/web.cpp` `ps2web_fetch`, on the main thread: 256 KiB chunks with `Range` inside `disc/NNN.bin` (64 MiB), default HTTP cache (no Cache Storage or IndexedDB), fixed 60 s timeout, validates 206 + `Content-Range` + exact length. On failure: the async path (`cdvd`/`cdvdfsv` jobs polling `disc::ready`) requests again right away, with no backoff; the sync path (`chunk()`: modules, `ioman`) 4 attempts at 100 ms and then **zeros** to the game (`disc::read` fills). A bad chunk is not stored as good (Chrome does not consider a cut response complete and the page rejects it), but it can be served again from the cache on the first attempt.
- **[DONE] Chrome HTTP cache lock** (a local test server + script): 4 ranges of the same URL, one with a 10 s server delay: with `cache: 'default'` all 4 end at 10 s (also if the server sends `no-store`); with `cache: 'no-store'` or `'reload'` the other 3 take 0.3 s. With a 16-chunk read-ahead on the same piece, a cold piece on the CDN stalls everything.
- **[DONE] Web reproduction** (headless Chrome, Fetch.requestPaused on `*/disc/*.bin*`, presses up to J's Bar, RMS of the audio ring; `serve.py` now serves the pieces like production). Chunk of the opening movie (`029.bin` +30 MiB, sector 965632):
  - Before, hung once: 60 s wait and **audio at 0 from there to the end** (frames 2500-8600), the game stayed at the title.
  - After, hung once: second attempt at 6 s, times equal to the fault-free run, normal audio.
  - After, 4 consecutive cuts (54 s without data): without the pause, audio dead anyway; with the pause (`disc::ready`), "pausing the game ... arrived after a 46.4 s pause", normal audio and reaches J's Bar. Ad-lib (`022.bin`, sector 747810) 54 s: pause 52.7 s, audio continues.
  - 500 x6 on chunk 8 at startup: before, zeros to the game ("ISO range read failed after retries") and the game stops reading the disc; after, it retries and starts. Truncated x3 and cut connection x3: retries and starts (`trunc 393216 B` in the counter).
- **[DONE] Cause of the dead audio (native, new `PS2_DISC_DELAY_AT=<byte>` in `disc.cpp`, delays only that chunk):** one single chunk of the movie delayed 15 or 50 s leaves the game without audio for the rest of the run; 6 s does not. The EE waits for the read (`cdvdfsv` fn 1) polling `S fn 4` and then continues, but the stream was already abandoned. [HYPOTHESIS] it is the CRI library's own timeout (~10 s of game time).
- **Fix:**
  - `ps2web_fetch`: `cache: 'no-store'`; a second parallel attempt if the first did not finish in 6 s; cut at 15 s without bytes; up to 8 attempts with backoff 0.25-8 s (+-25 %); validates length while reading the body. Counters in `Module.discStats`.
  - `chunk()`: never returns zeros; requests again with backoff (0.5-8 s) and logs it.
  - `disc::ready()`: if the same read has been waiting 2 s, emulation pauses until it arrives (the game sees at most 2 s). Online, a player with a very bad network stays frozen meanwhile (before, it continued, but without sound).
  - Bug report: field `discio` = `req ok fail retry hedge gaveup slowest ms @offset trunc B, MiB, pending, last: error`.
- **Own cache (outbreak `40bbd91`):** `no-store` only changes the network; every chunk that arrived complete and verified is stored in Cache Storage (`reo-disc-v1-<disc size>`, key `disc/NNN.bin?r=<offset>-<size>`, without going through the CDN) and read from there first. `?r=` was discarded in the network URL: the CDN would store one object per range and request them from the origin. Measured with the same Chrome profile: 1st visit 109 chunks over the network and 109 stored; 2nd visit **0 network requests** (only the `000.bin` HEAD), 109 from the cache and normal startup. Truncated x3 on the 1st visit: the bad one is not stored; the 2nd reads it fine from the cache. Movie with 54 s without data: 46.8 s pause, normal audio and reaches J's Bar. File #2 compiled and starts (52 chunks, 1,500 frames). The report adds `cached`. No own limit: the browser may delete the cache if space is short (best-effort); at most it stores what was read from the disc (a few hundred MB per scenario).
